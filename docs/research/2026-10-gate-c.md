# Gate C: Personal Configuration and Credentials

**Date:** 2026-10-09

**Result:** Pass

**Plan:** [Baseline Experiment](../plans/2026-10-baseline-experiment.md#gate-c-personal-configuration-and-credentials)

**Scripts:** `experiments/gate-c/`

---

## Summary

A chezmoi source embedded read-only in the image seeded a new home once, on first initialisation of a data disk, and was not reapplied after a restart. A user edit to a managed file, Claude Code's own state, and its subscription login all survived the restart. A host broker stub resolved approved bindings from a 1Password service account and delivered them over vsock into the environment of a single guest process. The service-account token never left the host. Every failed binding stopped the launch before the command ran, with an error naming the binding and the reason.

Claude Code worked with two subscription paths and no API key: a `claude setup-token` token stored in 1Password and delivered by the broker, and an interactive `claude` login over SSH. A host leak scan found no service-account token, 1Password value, or setup token in the root image, data disk, logs, work directory, or repository. The interactive login's tokens were only in Claude Code's credential file on the data disk.

The host was the same nested-virtualization DigitalOcean droplet as Gates A and B. The broker is a stub; its socket-path identity stands in for real guest authorisation.

## Findings

1. **Interactive Claude Code login works over SSH without a browser.** The login URL was opened on the client and the code pasted back. Claude Code stored the login as plaintext JSON at `~/.claude/.credentials.json` (mode 600, 504 bytes), with access and refresh tokens under `claudeAiOauth`. It persists on the data disk, so backups of user data contain a usable subscription login.
2. **A `claude setup-token` token works as a broker binding.** Delivered as `CLAUDE_CODE_OAUTH_TOKEN`, it authenticated Claude Code without writing a credentials file, so a subscription login can be delivered per session and kept off persistent storage.
3. **Claude Code writes configuration beside chezmoi-managed files.** On first run it created `~/.claude/settings.json`, `history.jsonl`, `projects/`, `sessions/`, `backups/`, and other state inside `~/.claude`, the directory chezmoi created. Dotfiles must manage individual files there, never the files Claude Code writes, such as `settings.json`.
4. **chezmoi reports user edits without overwriting them.** After the edit, `chezmoi status` showed `MM .claude/CLAUDE.md`. This is input to the conflict-workflow open question; applying a newer dotfiles revision was not tested.
5. **chezmoi works from a read-only source.** Its configuration file, which sets `sourceDir`, is written to `~/.config/chezmoi` on the data disk; chezmoi needed no writable path outside the home.
6. **New home files are group-writable.** The default umask in the guest gives `rw-rw-r--` to files such as `CLAUDE.md` and `settings.json`. `dev` is the only member of its group, so this has no effect in a single-user guest.
7. **The leak scan needed two fixes before its result could be trusted.** Its first pass reported the root image clean while scanning a nonexistent path, and `grep` silently matched nothing in the 20 GiB sparse data image because runs of zero bytes form single huge lines. The scan now uses NUL-delimited search (`grep -z`) and treats unreadable files and `grep` errors as failures. The rerun found the known Claude Code tokens in the data disk's raw blocks, confirming the search works.
8. **The broker never sees the guest's identity.** Each Firecracker VM has its own host-side vsock socket, so the socket path implied the environment. Nothing authenticates the request beyond that.

## Decisions

- **Personalisation:** chezmoi applies an image-embedded, read-only dotfiles source once per data disk, recording its revision and managed files under `~/.local/state/boxface/`. Later boots never reapply it.
- **Credential delivery:** The guest requests bindings by ID over vsock; the host resolves only approved bindings and returns values for the requesting process's environment. Failures stop the launch with a binding-specific error and no fallback.
- **Claude Code authentication:** Both subscription paths are supported. Interactive login stores agent-managed state in the persistent home; a setup token can be delivered by the broker per session.

## Not Covered

- Real guest authorisation for broker requests; the socket path stood in for it.
- Applying a newer dotfiles revision to a seeded home and resolving conflicts.
- Authentication for Codex, OpenCode, and Pi.
- Token rotation, revocation, and expiry of a delivered setup token.
- Delivery to sessions under tmux or another session manager.
- Backup handling of agent login state.
- Bare-metal timing on the ThinkCentre.
